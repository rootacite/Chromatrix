# IPC (`api.py`) — Chromatrix

> Detail behind `AGENT.md` §6. `AGENT.md` keeps the condensed rules; this file carries the full text.


Framing: one JSON object per WebSocket text frame. `{id, method, params}` → `{id, ok: true, result}` or `{id, ok: false, error}` (plus `code`/`holder` on a refusal).

**One client at a time, and no server-side locking.** A connection is admitted by `hello {client, instance, lane}`: the first instance owns the helper, the same instance may open as many connections as it likes (the desktop's four lanes), and any other instance is answered `{"ok": false, "code": "CLIENT_BUSY", "error": "<client> owns the training helper (since HH:MM:SS); close it and retry"}` and closed (`api.ClientSession`, `_OWNER_GRACE_SECONDS = 5`). There is no takeover request — the helper is released five seconds after the owner's last connection is gone. A first request *without* `hello` claims a free helper (the compat path for scripts), and a connection that never sends a request (the desktop's `helperListening` probe) claims nothing. The server takes no lock of its own: `dispatch` runs the handler directly, and keeping two calls that fight over the same resource off the wire is the client's job (`IpcResources`).

`dashboard` synthesizes `Train/Avg_Loss` from `Train/Loss` via `synthesize_avg_loss` when the tag is missing (old runs). Do not rename TensorBoard tags without updating Chromatrix chart cards. It also keeps **one `EventAccumulator` per run directory** (`_tensorboard_reader`, keyed by resolved dir, dropped when the newest event file changes or shrinks) and reloads it in place, so a poll reads only the events written since the last one — the read was 255 ms at 24 k points when every call re-read the file from the start, and is 4.6 ms now; a live run's poll after 200 more steps measured 20 ms (the reply's own size is what is left, which is why the plan's `start_step`-scoped reply is still on the table). `_TB_CACHE_LOCK` guards that cache; it is the only lock in the helper and it spans one function.

`generate_sample` / `generate_checkpoint_samples` / `evaluate_checkpoint` share one gate (`_claim_generation`: `_gpu_busy` — the `_TAG_BLOCKED` statuses with a live PID, so `paused` passes — and `_running_generation`, which scans **every** run's `generated/*.json` because the GPU is single-tenant and closes a job whose PID is gone). The API's own `dataset_tag` guard uses the same `_gpu_busy`.

Every job record carries the `step` of the checkpoint it renders (`_checkpoint_step`: the artifact directory name, else `ss_steps` in its metadata), because that is what the Dashboard attaches the images to; a job with none renders into `generated/` and is shown nowhere. Its counters (`current_step`, `total_steps`, `images_done`, `total_images`) are always integers — the client declares them `Int`, and an explicit `null` fails its decode and takes the whole `list_generated_samples` reply down with it. `TrainerIpcClient`'s `Json` sets `coerceInputValues = true` for the same reason: one bad record must not hide every generated image.

A `batch` job (`new_batch_job`) is the plan of a step-range pass and holds **no images at all**: it lists the checkpoints in render order and tracks `checkpoint_index` / `images_done` / `failed`, while each checkpoint's images live in its own `sets` job (with `batch_id` / `batch_index` / `batch_total`), which is what puts them on the right card. `mode: sets` and `mode: single` records may carry `cancel_requested`: `cancel_generation` signals the process and sets that flag, the job stays `running` until the process is really gone (the card is not handed over before that), and then closes as `cancelled` with whatever `files` it wrote. `JOB_CANCELLED` / `jobHasImages` in Chromatrix mean those images still show — the rule is "no longer running and has images", which also keeps a failed pass's partial images visible.

An `evaluate` job (`new_evaluation_job`) is the other plan-like record: `plan` says how many whole passes of the config's sample sets it renders to top the checkpoint up to `depth` (`passes`, `per_pass`, `existing_images`, `render_total`, and the repeat indices each set writes — none at all when the checkpoint already holds `depth` images), `images` is the set being scored — the run's own samples at that step included — each entry carrying the prompt it was rendered from, `sample_sets` is what the top-up renders with, and `config_source` is the `config.toml` those prompts came from. Its `phase` (`rendering` → `tagging` → `scoring` → `done`) says which of `images_done` / `total_images` the counters belong to, and `scores` carries both boards when it ends (per-image micro and per-prompt union, plus the per-prompt breakdown and the tags that cost the most). `api._checkpoint_run` prefers the run the checkpoint's own path names over the one the request resolved, so a past run's checkpoint is evaluated with *its* config and topped up beside *its* samples.

Kotlin client: match replies on `id`. Every lane introduces itself with `hello {client, instance, lane}` (`clientName` per platform, `instanceId` random per app run), and a `CLIENT_BUSY` refusal comes back as `HelperBusyException` with the helper's own sentence — shown in place, never retried, and never answered by spawning a second helper. The client keeps **four connections** (`LaneKind` in `TrainerIpcClient.kt`), because each one is served in order by a single thread on the helper's side: `control` (every call that writes, so their order is the order they were made in), `poll` (reads — the Dashboard's chain, `train_status`, `hardware_status`), `blob`, and `long` (anything whose claims include `gpu`, a `dataset:` folder, a `path:` target or a `automation:job:`, i.e. what a tagger or an export can hold for minutes). Measured against a real helper: 185 polls during a 9 s `dataset_tag`, worst 17 ms. Each connection reconnects on its own when its reader sees the socket close, and each call has its own budget (`IpcResources.timeoutFor`: 15 s default, minutes for the tagger and an export) — a call that never answers fails instead of holding its resources for the session, and a reply that lands after that is dropped (ids are never reused per connection). `ignoreUnknownKeys = true`. Keep that when adding fields. Do not add a generic `read_file` / `write_file`.

**The app's own locks live in the client** (`data/IpcResources.kt`): api.py serves **one** client session and takes no lock of its own, so nothing on the server orders two calls — the app must not put two calls that fight over the same thing on the wire at once. Each resource name has a read/write lock (`ResourceTable`: any number of readers, or one writer, taken in name order so two calls can never deadlock) and a per-method policy row decides what a call claims and how long it may wait: the training controls wait 5 s for the runtime files, the small stores 1 s, and anything a long job can hold — `gpu`, `dataset:<dir>`, `path:<dest>`, `automation:job:<id>` — is refused **at once** (`IpcBusyException`: "dataset_tag is using dataset:/data/st (41 s)") instead of queueing behind ten minutes of work. Reads claim only resources that are rewritten wholesale (`config`, `profiles`, `run:<id or current>`, the automation stores); `dataset_list` and `blob_*` stay unlocked on purpose, because locking them would put a tag in front of the Images page. `TrainerIpcClient.call` takes the claims **before** it touches the socket and releases them when the reply lands (a lock released earlier would only look like ordering).
