# Chromatrix

> Detail behind `AGENT.md` §7. `AGENT.md` keeps the condensed rules; this file carries the full text.


Compose Multiplatform **desktop JVM** plus a **wasmJs** local/LAN companion (`:webApp`). Kotlin 2.4.10, Compose 1.12.0, Material 3, Metro DI, ktoml, Coil 3, haze 2.0. Visual style follows KataHana's porcelain cards and Nunito, on an amber night palette (`RankoPalette.Amber`). Raw hex lives only in `ui/theme/Color.kt`. The brand accent is the logo amber `#F8A818` (the field is still `accentPink`, which every screen already reads as that accent). Screens read `rankoColors` / `PorcelainCard` / `CapsuleButton`; Canvas helpers take colors as parameters.

User-facing look-and-feel (background: Solid / Glow / Image, independent card vs background blur, font/icon scale, thumbnail JPEG quality) lives in the **Appearance** section of the Utils tab and is persisted by `AppearanceRepository` (Java Preferences, key `com/acite/axlranko/appearance`). `App.kt` consumes it and feeds `LocalDensity` so **font scale only affects sp** and **icon scale only affects dp** (`density * iconScale`, `fontScale * font / iconScale`). `RankoBackdrop` renders glow orbs for `Glow` and a cropped, dimmed photo for `Image`. A full-window haze layer uses `backgroundBlurRadiusDp` (gaps); `PorcelainCard` / `FrostedSurface` use `cardBlurRadiusDp`.

The Utils **Training** section ends the Epochs / Batch size / Grad accumulation / Val split % row with the run's expected size (`StepEstimateLine` in `pages/UtilsScreen.kt`): `≈ N steps · S/epoch × E epochs · M samples/epoch`. The image counts come from `dataset_counts`, fetched when the section opens and again (debounced 400 ms) when the folder list, `val_split_percent`, `val_data_dir` or `seed` changes — the epoch/batch/GA arithmetic is `estimatedSteps` in `model/StepEstimate.kt`, pure and local, so those keystrokes cost no IPC. `trainingSamplesPerEpoch(counts)` subtracts the `val_samples` the helper reports, which is the same split the dataset applies, so the estimate follows the run's real epoch length; the small print names the held-out images when there are any. It is a floor rather than a promise: the trainer's `BucketBatchSampler` carries one `ceil` per bucket while this does one over the total, and `enable_bucket = false` makes the two agree. `Val samples` and `Val interval` sit on the row under the estimate line (the interval's `0` = never run a pass; otherwise the first pass is step 1 and then every N steps). Below them, **Separate validation set** (`ConfigSwitch`) is the custom `val_data_dir`: turning it on runs the directory picker and only writes the path when one is chosen, turning it off clears it, and the selected directory gets its own `ConfigPathField`. While it is on, `Val split %` renders `enabled = false` with an `off while a separate validation set is on` note (the trainer ignores it and says so in the run log), while `Val samples` / `Val interval` stay live — they are read by the passes either way. **`Val split % = 0` with no directory is the feature's off switch**: `validationEnabled(form)` (in `TrainingConfigForm.kt`) is false there, so both fields render `enabled = false` with an `off while Val split % is 0` note and `validate()` stops range-checking them — the same exemption `TrainConfig.__post_init__` applies, so a stale value in a disabled field cannot stop a run with the feature off. The estimate line's small print names the validation directory's image count (`validation set: N images`) rather than a held-out part, and a directory the helper could not read (`val_data_error`) takes the estimate line's place with Retry, like a training folder's own error.

The Utils **WM** tab is the same kind of UI-only section (no config key) and is desktop-only by construction: `App.kt` provides `LocalAppWindow` (`util/AppWindow.kt`) from its `appWindow` argument, the desktop entry point passes `DesktopAppWindow` (`util/AppWindow.jvm.kt`) — Maximize applies the screen's own bounds to the window and remembers what it had, Restore puts that back, and Exit calls the entry point's own quit lambda, i.e. `ProcessExitGuard.armOnce()` plus `exitApplication()`, the same two steps the close request takes — and the wasm entry point passes nothing, so `visibleSections` (`pages/UtilsScreen.kt`) leaves the tab out of the web build. It exists for a session whose compositor draws no decorations (cage): there is no title bar to maximize or close from, and no window manager to act on a maximize request either, which is why the size is applied rather than asked for.

Home (`pages/HomeScreen.kt`) is the KataHana home laid out for this app. Wide windows (≥ 840 dp) use a 345 dp left column: the brand card (logo, Chromatrix, version, short git hash) and, filling the space under it, **What's new** — the last 40 commits, with the same kind chips as KataHana (`[Feat]` / `[Fix]` / `[doc]`, plus any git tag). The right column is a scrolling **Recent runs** list (`list_runs`; a row opens the Dashboard pinned to that run) with the five module cards under it. Narrow windows stack brand, changelog, runs, then cards. Each card is a `PorcelainCard` and opens that module through the same enter/leave path as the nav rail. Dashboard shows the live `train_status` line, a one-line hardware reading (`hardware_status`: GPU use, VRAM, GPU temperature, RAM use), a mini Avg Loss chart (the run's `Train/Avg_Loss`, no hit testing) and up to four samples from the newest step. Automation shows the running job, else the newest one, and that job's newest images (`recent_paths`, the last 24) in at most two rows sized to the card. Statistics draws a short non-interactive tag-frequency bar list. Utils lists config fields as **name**: value. Images shows a random sample drawn round-robin from every train-data folder, also at most two rows. Home polls `train_status`, `list_samples`, `list_runs` and `automation_job_list` while it is open, and calls `dashboard()` only to read `Train/Avg_Loss`. The poll stops when Home leaves.

Path pickers go through `PathPicker`. Desktop (`JvmPathPicker`) is FileKit (XDG portal on Linux). Web (`WasmPathPicker`) is an in-app porcelain dialog over `fs_listdir` / `fs_roots`, because the browser cannot return a POSIX path the trainer can open. Do not reintroduce `JFileChooser`. `initialDirectoryFor` seeds FileKit from the current field value; Save As on desktop may create a 0-byte placeholder that `deleteEmptyPlaceholder` removes.

Dashboard run history: `RunSelector` (`pages/components/DashboardWidgets.kt`, with the `runStampLabel` / `runDetailLabel` / `runStateLabel` / `displayedRun` helpers it renders) lists `list_runs` newest first and is what the whole page follows. Its first entry, **Current run**, clears the pin (`selectedRun = null`) so the page follows `state.json`; every other entry pins `DashboardUiState.selectedRun`. The run the page shows is `displayedRun` = the pin, else the entry whose id matches `dashboard`'s `run_id` (the trainer's own run) — with no run recorded there is none, so the box reads `Current run` / `Nothing started yet` and shows no run's figures. While following, the collapsed box keeps the title `Current run` and shows the run it resolved to underneath; a pinned entry titles that run's id instead. The only badge vocabulary is `runStateLabel`: **Live** while that run's process is running, **Stopped** otherwise, nothing at all when no run resolves (a `current` run is *not* labelled — it is Live or Stopped like any other). `fetchOnce` passes the shown run's `name` + `run_id` to `dashboard` / `list_samples` / `list_checkpoints` / `list_generated_samples` so charts, thumbnails and the checkpoint panel all come from that run; `TrainControlCard`'s identity line is that same run's (`controlRunName` / `controlRunId` in `pages/components/TrainControlCard.kt`, which fall back to `train_status`), so a history run with no logs and no samples is still named on the card. `trainingControlsEnabled` (`DashboardScreenViewModel.kt`) is the rule behind the control bar: the five buttons act on the run `state.json` is on, so they are all off while a past run is pinned (`TrainControlCard(controlsEnabled = …)`); `liveSettingsEnabled` adds "and that run is live" for the cadence/sampling controls, and without that the row shows `nextRunSummary` — `Next run · save every 100 steps · sampling on` from `config.toml` — because `state.json`'s `settings` block belongs to the run that published it (a runtime dir no run touched carries the placeholder `0` = "no checkpoints", which is not a configuration). `train_start` publishes the new run's values immediately after `mark_starting` (which clears the state), so the `starting` window shows the real cadence too. A `train_status.requested` block makes the row lead with the requested value — the switch and the cadence field show what was asked for, not the value still running — with a second line from `pendingSettingsLabel` (`pages/components/TrainControlCard.kt`) naming only what changed and when it lands: `Pending (applies at the next step)` while training, `… (applies from the next sample pass)` while `sampling`, `… (applies when the run resumes)` while `paused`. The blanket "changes apply at the next step" suffix is dropped while a request is outstanding, because it is wrong for a pass in progress. The Dashboard's pollers are **started on entry and stopped on leave** (`onEnter` / `onLeave`, called from `Stage.kt`'s nav rail): they used to keep running for the rest of the session behind whatever page the user had moved to, which is a seven-call chain plus an `nvtop` snapshot every second competing with the page actually on screen. Selecting a run drops the previous run's `chartPick` / `previewIndex`.

The Dashboard's **Sampling Prompts** section (`pages/components/SamplingPrompts.kt`) is the run's prompt editor: one line per set (name, prompt, `1280×720 · 55 steps · CFG 6.0 · seed 0 · ×3`) plus the source (`Edited for this run · sample_sets.json` / `From config.toml`), read lazily once per shown run through `sample_prompts` (never on the poll — only an edit changes it) and reloaded when the run changes. **Edit prompts…** opens `SamplePromptsEditorDialog` (a `Dialog` capped to the window and scrolling inside it, one `SampleSetForm`-shaped block per set with Add / Remove, saving through `sample_prompts_set`), and **Reset** (only while an override exists) asks first and drops the file, so the run samples with its own config again. The editor's field rules are `sampleSetFormErrors` in `model/TrainingConfigForm.kt`, extracted so the Utils Validation form and this one cannot drift; the payload↔form conversion, the labels and the clear-confirmation text are the pure functions in `model/SamplePrompts.kt`.

**Clear samples** is the card's destructive action (`clear_checkpoint_samples`): a card with images carries the button that removes them — the run's own samples at its step and the images of every pass the section shows on it, with the job records (and logs) that produced them — behind an `AlertDialog` that says how many go, since an image cannot be rendered again. `DashboardUiState.clearingSamplesPath` (one action at a time) plus the existing `gpuFree` / `busyElsewhere` rules switch it off, `clearSamplesResult` is path-scoped like `exportResult` so only that card reports it, and the page re-reads the run's samples and jobs from the same handler. A `samples only` row has no checkpoint to resolve a run from and so no button.

The page's last section is **Checkpoints**, not a sample gallery: `pages/components/CheckpointList.kt` (`checkpointRows` / `CheckpointRow` / `checkpointRowLabel`) joins `list_checkpoints` (filtered to the run being shown) with `list_samples` and the generated jobs, so every card is a checkpoint with the images of its step. A job joins the card whose `checkpoint` path it names — the step is only the fallback for a record that names none — and any pass no card claimed gets a `samples only` row of its own rather than vanishing — or a `samples only` card for a step whose weights are gone (Reset keeps samples). The fullscreen preview cycles `previewList(state.checkpoints, samples, jobs)` — the same
`checkpointRows` → `sectionImages` list the section draws — so a thumbnail the page rendered always
resolves to an index when it is clicked; a preview built separately from the rows is how a
step-less pass ended up shown but inert. The Ctrl+click panel's own row uses `panelJobsForStep`,
which adds a pass rendered from the checkpoint it is showing to the jobs recorded at that step.

The user can **pin** a checkpoint (the card's pin button) and the pinned cards lead the section,
drawn on `PorcelainCard(emphasized = true)` — the accent tint and border that say "this card is not
like the others" — with a `Pinned` badge and a `CheckpointsDivider` (`N pinned · M more`) between the
two groups; the state is one run's, kept by the helper in
`<logging_dir>/<run_id>/checkpoint_pins.json` and read back through `checkpoint_pins` — Chromatrix never
writes that file. `checkpointRows(…, pinned = …)` is a stable partition of the section's own order,
so the pinned block keeps the newest-step-first order and a pinned card does not move when another
checkpoint is saved; a pin whose file is gone stays in the file and draws no card. The list is
cleared when the shown run changes, and `DashboardScreenViewModel.pinsWriteInFlight` keeps a poll
that started before a pin write from putting the old list back over the reply.

Each card draws a mini Avg Loss chart (`CheckpointLossSpark` in `pages/components/CheckpointLossSpark.kt`) at a fixed 220dp immediately left of Save As, at least 82dp tall, which is the three header lines at the default type scale. In a portrait viewport that chart is the row under the title, full width and exactly `CheckpointSparkMinHeight` tall, and the card's buttons are icons. It has a background, grid and axes, and no tick numbers or border. It is the run's `Train/Avg_Loss` smoothed once with a fixed EMA weight of 0.85 — the same recurrence as the big chart's smoothed stroke, and not the smoothing slider — over at most `± 2 ×` that run's own snapshot `save_every_n_steps` (`dashboard.save_every_n_steps`, which is null rather than the repo file when the run has no snapshot). The run's `Val/Avg_Loss` is smoothed the same way and cut to the same window, and drawn as a second, gray curve (`SparkCompareLine`, `#9E9E9E`) **under** the slope-colored one; the two share one y range, which spans the windowed values of both, so the held-out curve reads directly against the training curve it is compared with. Fewer than two of the gray curve's own points in the window leaves it out and the range is the training curve's alone (`layoutCheckpointSpark(points, comparison = …)` in `CheckpointLossSpark.kt`; `DashboardScreen` keeps one `smoothAvgLoss` per series and passes both into every card). A vertical marker at the card's step shows where that checkpoint sits, and each drawn segment is colored by its own slope on that smoothed polyline. The steepest rise among the drawn segments is `(255, 79, 0)`, the steepest fall is `(0, 255, 127)`, and a flat slope is the midpoint. The scale is that drawn polyline's max |slope|: scaling by the steepest per-step move of the full series parks every segment on the midpoint, which reads as green. The chart does not take clicks, hover, or the big chart's step window and Y clip. A card with no step, or a run with fewer than two finite points, draws no chart.

**Save As** is one flow with two entry points — the Ctrl+click panel and every checkpoint card —
because the copy is the helper's job (`checkpoint_export`; Chromatrix has no path into `output_dir`).
`saveCheckpointAs(checkpoint)` asks the OS for a destination, copies off-thread and reports into
`DashboardUiState.exportInFlightPath` / `exportResult` (a `CheckpointExport` carrying the source path,
so the line shows only on the card or panel it belongs to; `CheckpointExportStatus` renders it for
both). One export at a time: the second request is ignored and every other button is off while the
dialog or the copy is open.

Above the cards, `SampleRangeRow` (in `DashboardScreen.kt`, with `checkpointSteps` / `checkpointsInRange` / `batchRangeError` from `CheckpointList.kt`) is the step-range control: it prefills the run's own steps, says how many checkpoints the range covers, and starts `generate_checkpoint_samples_batch`. While a batch runs the row shows `runningBatch`'s progress (`batchProgressLabel`) with a **Stop** button that calls `cancel_generation`, and `runningJob != null` is what switches every per-card button off (a batch holds the card like any other generation). Once anything is pinned, the same block shows **Generate pinned samples** (`PinnedSampleRow`), which starts `generate_pinned_checkpoint_samples`: one detached batch over every valid pin, in pin file order, with the same progress line, Stop and error display as the range batch (`batchHeadline` names the pin list instead of a step range, from the record's `selection`). It is enabled while the GPU is free and no batch is running, and a pin whose file is gone is simply not rendered (the helper drops it; with no valid pin the call refuses and the refusal lands on the section's error line). A checkpoint with no images gets a **Generate samples** button that calls `generate_checkpoint_samples`; it is enabled only while no live trainer is using the GPU (`generationAllowed` = `!alive || status !in GPU_BUSY_STATUSES`, mirrored by `api._gpu_busy`), which is what makes a **paused** run samplable. The Ctrl+click panel's own `Generate sample` button passes that same `gpuFree` rather than reading `alive` directly: the two used to disagree for a paused run, and the raw PID check is what left the panel disabled over a run that had finished (see `status-machine.md` on zombies). Generated jobs live on `DashboardUiState.generatedJobs` (they used to sit inside `ChartPickState`), and `generatedSampleItems(job)` expands a `sets` job — and an evaluation, which names its files the same way — to one `SampleItem` per file, reading the `Pn` set from the file name.

**Evaluate** is the card's second action (`evaluation`'s plan is in `ipc.md`, its metrics in `trainer.md`). The card carries only the entry point — the **Evaluate** button for a checkpoint that has never been scored, else a capsule reading `Evaluation · Recall 0.62` / `Evaluation · running…` / `Evaluation · failed`, and a running pass keeps its phase progress + **Cancel** row — while everything else lives in `EvaluationDialog` (`pages/components/EvaluationDialog.kt`), which is a panel rather than a start-only dialog: it shows the job it was opened on (recall as the headline, `P`/`F1`/images quiet under it, the union/coverage/config/scored-tags lines, `Details` for the per-prompt breakdown and offenders, `Cancel` while it runs) and, under that, the form that starts another. The panel is given the room the window has (`maxWidth` / `maxHeight` from the page's `BoxWithConstraints`, minus `PAGE_PANEL_MARGIN`) and scrolls its content inside it — Compose draws this `Dialog` as a layer in the same window here, so without the cap a long result or prompt list is drawn past the bottom edge and its buttons become unreachable; `CheckpointsSectionRenderTest.thePanelScrollsInsideAShortWindow` measures the panel's own `ScrollState` viewport (the state is hoisted for exactly that) against a 760×420 window. The form asks for depth (prefilled with the images the card already shows, because the depth is a floor), a tagger threshold, the tagger's categories (fetched once through `tagger_info`, a single `general` pill when the helper cannot answer, exactly as the Utils Auto-tag card degrades) and **Prompt tags to score**: the tags the run's prompts ask for, from `evaluation_prompts`, drawn as a frequency list (`TagFrequencyList`, the same ramp Statistics uses) that narrows the scoring to the clicked tags (`{}` = every tag the prompt asks for). The rules behind it are pure functions in `pages/components/EvaluationRules.kt` (`evaluationRequestError` mirrors api.py's ranges, `evaluationRecallHeadline` / `evaluationSecondaryLabel` / `evaluationUnionLabel` / `evaluationCoverageLabel` / `evaluationTagsLabel` / `evaluationConfigLabel` build the panel's lines, `evaluationDetailRows` its details block, `cardEvaluation` picks the job a card reports on: the one still running, else the newest finished one). The panel is opened from a card's Evaluate button (`openEvaluation(checkpoint, images, jobId)`) or from its evaluation capsule (`showEvaluation(jobId)` — a job whose checkpoint a Reset removed still opens, from a stand-in built off the job), it stays open on the pass it started, and `uiState.generatedJobs` keeps it live while the page polls.

Which jobs a card shows is `jobShowsOnCard` (`ChartPick.kt`), not `jobHasImages`: an evaluation that rendered nothing at all — the checkpoint already held enough images, so it went straight to tagging — has no `files` and would otherwise take its scores down with it. That predicate is what `checkpointRows`, `generatedJobsForStep` and `panelJobsForStep` filter on, so a scored-but-imageless evaluation still lands on its checkpoint's card (or on a `samples only` row when the weights are gone, where its score is still shown).

Dashboard charts: the training charts draw an always-on hover cursor with the exact step under the pointer, and mark the clicked step (dashed) plus the step a pick matched (bold, flagged). **Train / Avg Loss** is a three-series `MultiSeriesChartCard` (legend on): `Avg Loss` (`Train/Avg_Loss`, `accentPink` = the brand amber), `Val Avg Loss` (`Val/Avg_Loss`, `accentBlue`) and `Val Fixed Loss` (`Val/Fixed_Loss`, `accentRose` — the palette's one true pink `#E87FA8`, added because `accentPink` is the amber accent), sharing one x axis, one smoothing/Y-clip window and the same `Ctrl`+click picking; the epoch marks come from the latest step across all three. The click panel's `TRAINING_STAT_TAGS` row list carries `Val Loss`, `Val Avg Loss` and `Val Fixed Loss` between `Loss` and the LRs, so a run without those series keeps the row shape with an em dash. Every chart whose x axis counts steps opens on the newest 800 steps (`DEFAULT_STEP_SPAN`, applied by `initialXWindow` in `pages/components/ChartCard.kt` — the same windowing `Ctrl`+wheel zoom uses; the Steps slider above the charts changes it, and the Y clip slider (default 15%) sets the percentile tail applied **per series to the smoothed curves**, the y range being the union of the per-series ranges. `fittedYRange` in `ChartCard.kt` carries the reason: pooling the series into one list lets a dense training curve decide the percentiles and trims the sparse validation curves' own values off the axis, and the fit never reads raw points (only a series' newest smoothed point is forced inside). The smoothed stroke is 1.2 dp thicker than the raw one by default (Smooth + slider). Steps, Y clip and that extra are stored in the run's `chart_view.json`), and fits its y range to the smoothed points inside that window, expanded so the newest point stays visible. Epoch boundaries on Avg Loss are labelled with the epoch number alone. The hardware charts' x axis is time, so they keep their whole range. The `Learning Rate` card is a `MultiSeriesChartCard(axisCount = 3)`: each of the first three series is drawn through its own range and labelled on its own axis (`axisTickValue`, `ChartAxis`, `assignAxisDomains` — each curve fitted and clipped on its own values inside the window, since they differ by orders of magnitude), the UNet LR on the left and the other two stacked in the right gutter, innermost first; `rightAxisLabelX` places those columns and the outermost is right-aligned to the card edge, which is where the two-axis form put its single right label. Its third series is the **stability curve**: `rollingPopulationVariance(Val/Fixed_Loss, steps_per_epoch)` (`ChartVariance.kt`) is the population variance of the raw fixed-loss points inside the closed window `[step - steps_per_epoch/4, step + steps_per_epoch/4]`, drawn in emerald (`ChartVarianceLine`, `#10B981`) under the legend `Val Fixed Var`; a window holding fewer than two points yields no point, and with no `steps_per_epoch` (or fewer than two variance points) the series is dropped and the card is the two learning-rate curves alone. The chart's own smoothing slider still applies to the drawn curve; the variance itself is read off the raw series. Every other chart keeps the single shared 0..100 axis. The **Train / Avg Loss** card additionally owns the checkpoint panel, opened by `Ctrl`+left click or by a left double click — the pick fires on the *picking* click, so a double click anchors at the second click, and the 400 ms window rule lives in `completesDoubleClick` (`pages/components/ChartPick.kt`). The panel shows the matched checkpoint highlighted, the clicked step's `Avg Loss`/`Loss`/UNet+TE LR, that step's samples with any generated ones, and can be dismissed by a click outside / close / `Esc`. It is resizable by dragging its bottom-right grip: placement is decided once from the click and the *default* size so a drag can never move the panel (`placePanelOrigin`/`clampPanelOrigin`), and the slots fill the dragged width (`sampleSlotWidth`, no 400 dp cap) with extra images wrapping instead of scrolling. `Save As` asks the OS for a dest path then calls `checkpoint_export` — the same flow a checkpoint card's own `Save As` uses (see the Checkpoints paragraph above); `Generate sample` renders one extra image per `trainer.md`. Sample and dataset images load through `blob_batch` (Coil `BlobRef`), never `java.io.File`.

Dashboard chart interactions are shared only by the three step-axis cards. Their curve legend entries toggle visibility; hidden series are omitted from Y clip, Y bounds, drawing and their multi-axis domain. X Move/H Zoom is shared, Y Move/V Zoom remains per chart, and the hover cursor synchronizes to the same logged step on all three. The first manual edit enters `Detach`, which lives in `StepChartInteractionStore` inside the Dashboard ViewModel so lazy-list disposal and data polls cannot reset it. Steps/Y clip sliders defer their re-fit until the `Reset` button restores automatic viewports. Switching runs clears visibility, hover and viewport state.

Dataset scan in the GUI is **non-recursive**, one folder, image + same-stem `.txt`. Orphan captions **abort** the statistics scan. `ranko/tools/agent.py` mirrors this (`--allow-orphans` to inspect anyway). Trash for GUI/agent drops: `/tmp/axlranko/trash` (not the dataset’s own `trash/` used by some `tools/` scripts).

Statistics → Control Panel **Shuffle & Renumber** is IPC `dataset_shuffle` (`trainer/fsrpc.py`): one group per stem (image(s) + `.txt` + `.mask.png`), temp `axl-shuffle-*` names, then `0001…`. The group keeps a mask on its image. It refuses a folder with an orphan `.txt`. Kotlin `DatasetShuffle.kt` remains a jvmTest helper. The standalone `tools/suf.py` still splits on the last dot and therefore still separates `{stem}.mask.png` from its image.

Every page that changes dataset files on disk **must** call `DatasetRefreshHub.notifyDatasetChanged()` — Statistics' tag edits, drop and shuffle, Utils' tagger, Images' caption save. Images and Statistics both cache the folder and reload off that hub (`reloadFromDisk`, `scanDataset`), and its buffer drops the oldest signal rather than refusing a burst. The other direction needs no signal: the nav rail scans Statistics on entry. The Statistics → Images thumbnail jump has to rescan too (`selectItemByTxtPath` always reloads with the jump remembered) instead of selecting out of the cached list, which is what used to show captions and samples the other page had already replaced. Images' reload keeps an unsaved caption draft only while the file still holds the text the draft was based on.

Mask edits stay in memory until **Save mask**. Invert / Fill / Clear / strokes set `maskDirty`; Clear is a pending sidecar delete; **Reset mask** restores the last loaded/saved snapshot. Navigation never writes a mask (`flushPendingMask` is gone). Raster is a `ByteArray` (`MaskCanvas`). Desktop `maskPaintInput` is AWT + 4 ms `MouseInfo` poll; wasm is document pointer events + a 4 ms interval. Compose pointer APIs still report the primary button only, which is why those actuals exist. The same listener reports every pointer position (`onPointerMoved`, throttled to 16 ms by `MaskPreview` for the brush cursor) and handles Alt+wheel brush resizing (`onBrushResize`; `util/MaskBrush.nudgeBrushRadius` owns the step and range). Coordinates come from `LayoutCoordinates.boundsInWindow()` in that modifier.

Screen→window conversion for the sampled pointer must go through a component **inside** the window (`window.contentPane`), never through the `Window` itself: a `Window`'s screen position is its frame origin including decorations, so converting through it lands `insets.top` pixels off — 41 px under KWin/XWayland — and half the samples then paint a parallel line offset from the other half. `MaskPreview` maps box coordinates to image coordinates and drops samples outside the drawn image, calling `onStrokeLeaveImage` so a stroke that leaves the image resumes as a new segment instead of smearing along the border. Brush math lives in `util/MaskBrush.kt` (falloff, path interpolation, blending) and raster ops in `util/MaskCanvas.kt`; both are unit-tested without a display.
